The content of agentic memory is fundamentally multi-modal. A
single “memory unit” may carry: (i) raw text (a chat snippet, a code
diff, a document excerpt); (ii) one or more dense vector embeddings,
often produced by different encoders for different retrieval objectives (e.g. semantic similarity, intent classification, code search);
(iii) structured metadata (timestamps, source, provenance, user tags,
confidence scores); and (iv) graph structure (entity relations such as
derived_from, cites, contradicts, member_of). A useful query
against this store is seldom a pure similarity lookup; it is a conjunctive expression that mixes all four modalities. “Find passages about
a fault tolerance bug from the last 30 days, semantically similar to
this stack trace, attributed to a known subsystem, and connected
by derived_from to a previous incident” is representative.
The dominant engineering response is multi-path recall: a fanout across specialized engines (a vector index, a full-text index, a
key–value store, a graph store), each producing a ranked candidate list, followed by application-level score fusion and re-ranking.
Frameworks such as Mem0 [14], Letta [15], Zep, and Cognee instantiate variations of this pattern. It works, and there is no shortage
of impressive product demonstrations. But the pattern has four
structural weaknesses:

Production LLM agents accumulate multi-modal memory across
two timescales: long-term facts and preferences, and short-term
working context. A memory unit typically carries text, one or more
dense vector embeddings, structured metadata, and graph relations.
Useful queries against this store are conjunctive expressions that
mix all four modalities — for example, “find passages about a faulttolerance bug from the last 30 days, semantically similar to a stack
trace, attributed to a known subsystem, and connected by a derivation link to a prior incident.” The dominant engineering response,
multi-path recall with application-level score fusion, has no principled semantics, no equivalence relation over plans, and breaks
down on multi-vector conjunctions. We propose MosaicOpt, an
algebra-first design that extends relational algebra with (i) a materialization operator 𝜇 that binds computed values (vector distances,
BM25 scores) as first-class attributes, (ii) first-class vector, text, and
graph predicates, and (iii) a graph expansion operator Γ. The optimizer is a Volcano/Cascades-style rule-based layer driven by an
equational theory of seven foundational identities (M1–M5, G1, G2)
over the extended operators, supplemented by the assumed classical
A1–A8 (including join commutativity and associativity; A1 and A4
apply naturally to vector predicates), the derived chains (M4+M1,
M5+G1, A4-vector+M1), the classical applications (A7-symmetry,
A8-regrouping), the definitional 𝜏-Λ-topK rewrite, and the rowpreserving 𝜎-𝜏 commutation, combined with a cost-based layer
that explicitly accounts for approximation. We prove the identities,
give counterexamples for the non-identities (N1–N5) that classical
intuition suggests but approximation, graph-traversal asymmetry,
or the traversal-vs-origin column split break, and sketch a prototype and evaluation plan. The argument is foundational: agentic
memory is a query problem, query problems benefit from algebraic
foundations, and the right foundation is an extension of relational
algebra.

1.2

Mathematical support for Agentic database
development

The algebra gives database researchers and engineers a precise
substrate on which to develop new query patterns and to prove
their correctness. A new materialization pattern (e.g., a new kind
of multi-modal fusion, a new join algorithm for hybrid vectors)
can be expressed as a new operator with a documented equational
theory — its rewrite rules are derived from the algebra, not guessed
from benchmarks. The optimizer’s plan space becomes a derivable
structure rather than a hand-tuned mess: each new operator is
added with its identities, and the optimizer gains the corresponding
rewrites “for free”. This is exactly the extensibility property of
Cascades; the algebra is what makes it principled.
A database system built on an algebra exposes a substrate capability: any application that can express its query in the algebra
can take advantage of the optimizer’s rewrites, and any physical
innovation that implements an algebraic operator improves every
application that uses it. This is the foundational insight: the algebra
is the common currency between the application and the engine.
Without it, every application negotiates with every engine on its
own terms; with it, an application written once is portable across
engines that share the algebra, and an engine innovation is portable
to every application that uses the affected operator. The algebraic
foundation is therefore not a research luxury — it is the contract
that makes the database ecosystem composable.

Why algebraic foundation?

Database systems have long benefited from formal foundations.
Codd’s relational algebra [1] and Selinger’s cost-based optimizer [2]
established that query processing benefits from a formal language
for what is computable and a formal theory for what transformations preserve semantics. The Volcano/Cascades line further
showed that the algebra is the API : a new operator is shipped with
its equivalence rules and cost model, and the optimizer gains new
capabilities without any central rewrite. An algebra is not an
implementation detail; it is the contract between query and
execution. When the algebra is rigorous, every query language
is a syntactic surface over it, every optimizer decision is auditable,
and every physical innovation is a drop-in.
Formally, an algebra provides four things that no collection of
indexes and APIs can:
• A language for expressive power — a precise definition of
what is computable in the system, and what is not.
• An equational theory — a body of identities that govern when
one query plan is equivalent to another, the foundation on which
any rule-based rewriter rests.

Four representative Agentic memory use cases illustrate what applications need from a substrate:
• Episodic recall (debugging copilots, personal assistants, “what
did I work on last week”): conjunctive vector + metadata + graph
queries, where a single memory unit is retrieved only if it satisfies
a similarity predicate and a time window and a graph reachability
test.
• Cross-session fact retrieval (long-term user preferences, learned
facts): single-vector or multi-vector recall with structured filters
(e.g., a user-scope, a topic filter, a confidence threshold).
• Working context assembly (short-term memory for an inflight session): fast filtered recall by recency + entity, where
latency dominates and the top results must arrive in milliseconds.
• Tool-trace analysis (multi-step agents, planning): graph queries
over derived_from and follows edges, joined with vector similarity on the underlying tool outputs.
All four are query problems — they are expressible as expressions
over a memory store, and they are amenable to the same optimizer
pipeline. All four benefit from a shared algebraic substrate: the
optimizer’s rewrites (M1–M5, G1, G2 foundational; A4-vector, A4vector+M1, M4+M1, M5+G1 derived; A7-sym, A8-regroup, topK
recognition, 𝜎-𝜏 commutation applied) apply to each, and the cost
model handles the modality-specific physics.
With MosaicOpt’s algebra, an Agentic application writes its
memory query in SQL (Section 5) or in the algebra directly; the
substrate applies M1/M4/M5-style rewrites to fuse materialization
with selection (and to push materialization through join and graph
expansion), applies G1 / V1 / J1 rules to push predicates down,
and applies cost-based physical-operator selection. The application
does not have to know about HNSW, B-tree, or inverted indexes;
the substrate hides these as physical realizations of a single logical
operator. The result is that an application that today writes its
own multi-path orchestrator — with hand-tuned per-channel top-𝑘,
hand-tuned fusion weights, and hand-tuned thresholds — can be
rewritten as a single SQL query, and get principled optimization for
free. This is the substrate contract in action: the algebra is what the
application writes, the algebra is what the optimizer rewrites, and
the algebra is what the engine realizes. The application’s policy
(the fusion weights, the thresholds, the top-𝑘) stays in the SQL; the
substrate’s responsibility (which index, which join order, which
approximation budget) is delegated to the optimizer.

The gap

What is missing is an equational view of multi-modal memory
queries in which vector distance, BM25 relevance, and graph reachability are first-class predicates on a par with 𝐴 = 𝑐; in which
computed values (distances, scores) are first-class attributes; and in
which the boundary between the application’s fusion policy and the
substrate’s evaluation strategy is explicit and contractually enforced.
That is the gap MosaicOpt addresses.
Figure 2 makes the contrast vivid. On the left-hand side (a), four
independent channels (vector, text, key-value, graph) each produce
a ranked candidate list, and application-level score fusion decides
the final ranking — there is no equivalence relation over plans, so
all optimization is heuristic. On the right-hand side (b), the user
writes a single logical plan over the extended algebra; the RBO
enumerates equivalent rewrites under the equational theory, and
the CBO picks a physical realization. The fusion policy is explicit
in the ORDER BY expression; the substrate has no opinion on the
weights.

The retrieval stack has evolved along a parallel track. Information
retrieval developed the vector space model [5] and BM25 [6] as
principled relevance scoring functions. The neural era added dense
embeddings trained for semantic similarity [7, 8], and approximate
nearest neighbour (ANN) indexes make these practical at scale.
HNSW [9] is the dominant ANN structure today, providing sublinear search with controllable recall via ef and M parameters.
A crucial property of HNSW — and of most ANN indexes — is
that they are approximate. The result of an HNSW range query is
not the exact set of points within distance 𝜏; it is an approximation
that misses some true neighbours (false negatives) and may return
some non-neighbours (false positives, depending on ef and the
distance threshold). This approximation is invisible at the level
of the algebraic query language: the user wrote 𝜎 ∥𝑉 −𝑞 ∥ <𝜏 (𝑅) and
presumably wants the logical answer. It is, however, central to
the cost model: a high-recall HNSW plan costs more than a lowrecall one, and the optimizer must be able to trade off recall against
latency.

The relational model [1] and the relational algebra that instantiates
it remain the dominant formal substrate for declarative query languages. Codd showed that a small set of operators — selection 𝜎,
projection 𝜋, Cartesian product, union, set difference, and rename
— is sufficient to express any first-order query. Subsequent work
refined the operator set (adding explicit ⊲⊳ for theta-join, grouping/aggregation, ordering, and limits) and crystallized in SQL.
The second foundational pillar is query optimization. Selinger’s
1979 cost-based optimizer for System R [2] established the template
that nearly every commercial RDBMS still follows: enumerate alternative orderings and access paths, estimate cost under a cardinality
model, pick the cheapest. The Volcano extensible query evaluation framework [3] and later Cascades [4] generalized this to a
rule-based outer loop driving a cost-based inner search, in which
equivalence rules over logical operators are first-class objects, and
the optimizer is itself extensible by adding rules. The insight of
Cascades is that the algebra is the API: a new operator is shipped
with its equivalence rules and cost model, and the optimizer gains
new capabilities without any central rewrite.
Two ideas from this tradition are central to our work. First, an
equational theory — identities over plans — is the necessary foundation for principled rewriting. Second, logical–physical separation
is what allows physical innovations (new access methods, new join
algorithms) to be plugged in without changing semantics.

Logical/physical separation

Following System R and Cascades, we treat the logical algebra as
the substrate contract — what the user asks for — and the physical
algebra as the engine contract — how it is evaluated. Equivalences
hold in the logical algebra; physical operators are implementations
of logical operators, and a logical equivalence does not in general
imply that two physical realizations are interchangeable (Section 4.5,
N1–N3). This separation is what makes the system composable:
HNSW can be added, swapped, or replaced without changing the
language the user sees.

Overview

The equational theory of the extended algebra plays two complementary roles. First, it is the foundation for the rule-based optimizer (Section 6): every rewrite the RBO performs is justified by a
foundational identity (M1–M5, G1, G2) or by a derived corollary
/ definitional / implied rule (A4-vector, A4-vector+M1, M4+M1,
M5+G1, A7-symmetry, A8-regroup, topK recognition, 𝜎-𝜏 commutation) — so the optimizer’s behaviour is auditable, not opaque.
Second, the non-identities (N1–N5) are the discipline that prevents
the optimizer from applying rewrites that hold in classical relational
algebra but break under approximation, graph-traversal asymmetry,
or the traversal-vs-origin column split. The cost model (Section 7)
is responsible for the physical cost of every rewrite; the equational
theory is responsible for its correctness.
Concretely, an identity is an equation of the form LHS = RHS
between two logical plans that hold for all instances of the free
variables (relation names, attribute names, query-time bound parameters). A non-identity is a pair of plans that classical intuition
might equate but the extended setting does not, with an explicit
counterexample. Both are first-class objects: the RBO loads them
as data, the cost model consults them when computing the “cost
of identity application” term, and the executor relies on them for
safety of adaptive re-planning (Section 7).
The structure of this section follows the algebra’s structure: inherited axioms (the ones we use but do not re-prove) in Section 4.2;
new identities (the ones the extended operators license) in Section 4.3; derived rules (combinations used directly by the optimizer)
in Section 4.4; and non-identities (counterexamples that bound the
optimization horizon) in Section 4.5.

RBO role

The RBO’s job is not to pick a plan. Its job is to generate a plan
space in which the CBO can search effectively. Concretely, the RBO
uses the equational theory to:
(1) Apply selection pushdown (A4, J1, G1) so that selective filters
are evaluated early and reduce the input to expensive downstream operators.
(2) Commute vector and classical selections (V1, A1) so that
the more selective predicate runs first.
(3) Reorder materializations (M2) and push materialization
through join / graph expansion (M4, M5) so that the expensive per-row computation runs only on origin rows rather than
on every join / traversal row.
(4) Expose topK opportunities by the definitional 𝜏𝑂 Λ𝐾 ↔
topK𝑂 recognition (the CBO applies it as a physical-realization

(5) Swap selection with ordering (the implied 𝜎-𝜏 reordering)
so a selective filter runs before a sort.
(6) Reorder joins using the assumed classical A7 and A8 to enumerate the 𝑂 (𝑛!) join orderings the CBO picks from.

6.5

Cross-modal plan enumeration (D)

For a single-modality query, the RBO’s canonical form is a small set:
one filter order, one materialization order, one join parenthesization.
For a multi-modal query — one that combines vector, text, graph,
and structured predicates — the canonical form is no longer obvious.
The predicates commute in principle (M1, V1, A1), but the costs
of evaluating them differ by orders of magnitude, and the join
parenthesization interacts with the modality ordering. The search
space is the product of the modality ordering and the join orderings.
MosaicOpt’s D contribution is a modality-aware plan enumeration that keeps the search space small without giving up the optimal plan. The RBO exposes the full equivalence class (rather than
collapsing to one canonical form), and the enumeration prunes
aggressively using per-modality cost estimates:
• Modality ordering. If two predicates have selectivities that
differ by an order of magnitude, the enumeration prunes the
order in which the less-selective predicate runs first; the cost
model already knows it would be slower. In practice, the modality
ordering collapses to 1–2 viable candidates per query.
• Join + modality co-enumeration. The 𝑛! join orderings and
the modality ordering are not independent: a join’s hash-build
side has different per-modality scan costs. The enumeration interleaves the two, using the modality cost to prune join orderings
where the expensive modality sits on the build side of a hash
join.
• Index-aware pruning. If a modality’s index does not exist on
the target relation, all plans using that modality as an early filter
are pruned. (E.g. a BM25 inverted index missing on a column
means the 𝜎 must run as a post-filter, not a pre-filter.)

6.6

Style: Volcano/Cascades

Our RBO is modeled on the Cascades framework [4]. Equivalence
rules are first-class objects, organized by operator pair (e.g. one rule
for 𝜎 × 𝜇, another for Γ × 𝜎). A memo structure caches explored
expressions and their cost bounds. The implementation language
is intentionally simple (Section 10); the interesting code is the rules,
not the engine.
The key consequence: adding a new operator is adding rules.
There is no central optimizer loop to modify. A contributor who
wants to support, say, a temporal range join, writes the operator,
the equivalence rules that reference it, and the cost-model entries
— and the optimizer gains the new capability. This is the property
that makes the algebra the API.

A traditional CBO minimizes a single weighted sum of the cost
dimensions and selects one physical realization. MosaicOpt’s CBO
treats approximation as a first-class fourth dimension: the search
is over the plan space of physical realizations, and any plan whose
estimated approximation cost exceeds the user-specified budget
𝜌 min is pruned before its other three dimensions are even evaluated.
What remains is a Pareto frontier over (I/O, CPU, memory) under the
approximation constraint, from which the CBO selects the optimal
point (or returns the entire frontier if the application is willing to
trade latency for memory).
The CBO consumes the per-modality cardinality estimates produced by the statistics layer of §7.3: each modality filter’s selectivity
is read from the StatisticsHub rather than the default 0.5 prior.
The strategy table that maps estimated selectivity to ANN strategy
(flat / ivf / hnsw) is then applied per filter. Algorithm 3 gives the
implementation.

Adaptive re-planning (B)

A gives a planning-time recall guarantee, but only as accurate as the
cost model. The estimated recall of an HNSW plan is recall(ef , 𝑀),
which is a fitted curve over a calibration sample. Real workloads
drift from the calibration distribution; cluster boundaries shift;
query patterns change. The estimated recall can disagree with the
observed recall.
Section 7.6 closes the gap with adaptive re-planning: at welldefined plan points in the physical execution — after an HNSW
scan returns its candidate set, after an inverted-probe returns its
postings, after a graph expansion returns its reachable set — the
executor pauses, observes the actual cardinality and a small-sample
recall estimate, and re-consults the cost model. If the observed recall
falls short of 𝜌 min , the executor switches to a higher-recall physical
realization of the same logical operator (e.g. larger ef, larger nprobe,
or fall back to flat scan). The algebra is unchanged; only the physical
subtree is replaced.
Safety. An adaptive switch is safe by construction: the new suffix is
an implementation of the same logical operator as the old suffix, so
the logical result is unchanged. The cost is bounded: the sampled
recall check is 𝑂 (𝑘) for a sample of 𝑘 rows, and the higher-recall
realization is selected from a precomputed set of ≤ 4 alternatives
(one per physical operator family).

Honest framing of E4. E4 shows that the CBO + cardinality layers
are infrastructure for scaling, not immediate wins on the prototype.
The statistics layer is ∼ 5 ms per call (§10.6); the 𝜌 𝑓 layer is ∼ 1 ms
per call. At 𝑛 = 104 , the underlying HNSW scan is ∼ 5 ms; the
optimizer overhead is comparable to the cost it tries to save. At
𝑛 ≥ 105 (see §10.6, E8), the HNSW scan grows sub-linearly but
the cost-model regime boundary becomes correct, and the CBO’s
choices matter. The point of E4 is not to claim the CBO always wins;
it is to verify that the cost model is honest: when the cost model
says HNSW is best, HNSW is best; when the cost model says flat is
best (at large 𝑛 + low 𝑠), flat is best. The CBO does not introduce
overhead that the user has to pay for in the small-𝑛 regime: the
adaptive policy skips the CBO on the prototype and uses HNSW
directly.

Synthesis: when does the CBO matter? The CBO + cardinality
layers form a conditional speedup stack: each module is the right
answer for a specific regime.
• Clustered filters (𝜌 𝑓 = 1.0): default_0.5 is best. The CBO’s

statistics layer feeds an accurate post-classical selectivity to the
cost model, and the cost model correctly identifies flat as cheapest on the small surviving set.
• Scattered filters at high selectivity: with_rho is best. The 𝜌 𝑓
estimation correctly identifies the fragmented surviving set and
demotes hnsw to flat, where the brute-force scan is cheaper
than the fragmented-graph traversal.
• Large 𝑛 (𝑛 ≥ 106 ): full is the right answer. The cost model’s
regime boundary 𝑠 = 0.05 becomes correct, and the CBO’s choice
of flat on the low-selectivity tail is load-bearing.

“default_0.5 is best” regime and the “full is best” regime. At

𝑛 > 𝑛 0 , the prototype invokes the full CBO + statistics + 𝜌 𝑓 stack.

derived from the cost-model scaling of §10.6 (E8).

11.3

Discussion & Future Work

MosaicOpt is a foundation, not a finished product. We close by
naming the limitations of the current proposal, the open problems
that follow from them, and the broader research context in which
the work sits.

2813
2814

11.1

2815

• Single-node, single-user. The algebra does not yet model partitioning, replication, or isolation. The cost model has no term
for cross-node I/O. A distributed extension is sketched below.
• Read-only. There is no write path. The algebra is defined on a
snapshot of the memory store. A write algebra would need to
model incremental updates to materialized views and to the cost
model’s statistical summaries.
• Approximation is a cost, not a contract. The cost model treats
recall as a dimension; the algebra treats queries as exact. There
is a real tension here, and we have not yet resolved whether
the user-facing language should expose approximation as a hint
(hint approx_recall=0.9) or as a contract (requires recall
≥ 0.9).
• Cost model calibration. The cost model requires empirical
calibration that we have not yet performed. A poorly calibrated
cost model is worse than no cost model, because it gives the CBO
a false confidence.

Connection to other research

2857
2858

The algebra draws on three threads.

2859

• Linear algebra. Vector distance is ∥𝑉 − 𝑞∥; an HNSW probe is a
linear-algebra computation. There is a natural research direction
in fusing linear-algebra kernels with relational operators at the
physical level — for example, a join that, in the same pipeline,
computes the distance to a query vector.
• Probabilistic databases. Approximation in HNSW is, formally,
a probability distribution over possible outputs. The cost model’s
“approximation dimension” is a step toward treating the database as a probabilistic system; a full treatment in the style of
probabilistic databases [13] is a natural extension.
• Programming-language theory. The materialization operator
𝜇 is, in spirit, a let binding in a query language. There is a natural correspondence with the let-binding extensions of relational
algebra used in query-language research, and the freshness condition for 𝑐 is a hygienic-rename condition. A type-theoretic
treatment of the algebra would strengthen the foundation and
make the rewrite rules easier to state and prove.

11.4

Closing

The argument of this paper is simple: agentic memory is multimodal, multi-modal is a query problem, query problems benefit
from foundations, and the right foundation is an extension of relational algebra. The algebra is small, the rewrite rules are provable,
and the optimizer is a direct consequence. We do not claim to have
solved agentic memory; we claim that the field will benefit from a
shared vocabulary, and we offer MosaicOpt as a starting point for
that conversation.

What the algorithm layer buys. The four algorithms compose
into a pipeline with the following guarantees: (i) the optimizer’s
output is reproducible — the RBO’s trace + the CBO’s Pareto frontier uniquely determine the chosen plan; (ii) the approximation

guarantee is two-tiered — planning-time via Algorithm 3’s 𝜌 min
check, runtime via Algorithm 5’s sampled recall; (iii) the search
space is bounded at every layer — RBO via the well-ordered weight
function, D via the modality-pruning rules, CBO via the approximation budget, B via the precomputed fallback set. The prototype’s
measured runtimes are: RBO ≤ 5 iterations per query (≤ 0.02 ms);
D produces 2–4 plans per query (≤ 0.05 ms); CBO enumerates ≤ 10
physical realizations per plan (≤ 0.5 ms); B is invoked at most twice
per query, each ≤ 0.1 ms. The total optimizer overhead is ≤ 1 ms
per query — small relative to the ANN build (25.77 ms) and range
scan (1.87 ms) costs the end-to-end experiment measures.
